# 依赖分析与深度定制

当前实测：受管源码 240 包（231 个基础包、9 个项目包），完整 Linux 解析图 239 包、WASM 解析图 233 包，唯一根锁包含 239 包。397 份原始发布归档全部保留；348 个活动原始身份用于审计，49 个原始来源明确退役。源码、宿主工具、构建脚本、派生宏、测试和目标解析图持续完整清点；250 仅为约数，不设包数硬上限。

优化目标是服务端、浏览器 WASM、资源编译器、构建脚本、派生宏和测试的实际实现质量：行为正确、资源开销合理、职责清楚、代码和维护成本可控。250 不是验收阈值，当前 240 包也不是停止优化的依据；合并或拆分应服从这些质量要求。完整图以根 Cargo.lock、本地源清单及两个目标的离线 metadata 共同核对；原始归档用于来源证明。具体当前数量和每个包的依赖见[源码清单](THIRD_PARTY_RUST_SOURCES.md)及[用途架构](RUST_SOURCE_ARCHITECTURE.md)。

## 分析方法

每个候选改动分别说明行为、支持面、编译边界与维护代价。重复实现可以统一，职责独立或编译代价过大的实现可以拆分；不要求包数单调下降。包数、目录改名与迁移工具通过不能代替设计审查或性能验证。对构建和性能收益采用同一工具链、配置、输入和环境的前后对比；缺少对比时明确记录未测量，不写成最优实现。

从实际入口递归检查每个依赖的消费者、启用功能、公开类型、宏展开及构建输入。先判断功能是否被博客使用，再判断能否合并。合并候选需要满足整个收缩后的图没有环，不能只检查两个包之间是否直接互相引用。

普通库合并为真实 Rust 模块，并统一依赖声明、条件编译和内部路径；旧包退出活动源码图。派生器的生成路径也要改到实际类型提供者。只改变 Cargo 名字、保留一套旧包清单，或者把旧别名同时指到一个包，都不算完成合并。

默认功能是消费者契约的一部分。把默认功能关闭后，必须显式保留产品需要的模块。例如路由器仍需 JSON、表单、查询和 HTTP 运行支持；正则库的 `matcher` 必须由原先使用 Regex API 的消费者启用。真实 Linux 和 WASM 编译用于捕获这类遗漏。

## 按用途收拢的实现

| 职责 | 源码收拢方式 | 必须保留的行为 |
| --- | --- | --- |
| CLI | 参数入口、参数模型及词法分析合入 `cli/arguments`；终端颜色、解析与输出另形成统一终端模块 | 派生宏、参数校验、帮助、非 ASCII 路径及终端判断 |
| 异步与 HTTP | Future/Stream/通道/执行器/工具收拢；HTTP body、路由、传输及服务组合各按协议职责收拢 | 流与取消语义、背压、HTTP 消息、适配器、限流及服务错误 |
| 序列化 | 核心 trait、派生支持及错误路径合入 `format/data-model` | 同一套 trait 身份、字段属性、中文 JSON、严格字段与错误位置 |
| SQLite | 查询引擎和 SQLite 驱动成为 `storage/sqlite-access` 内部模块；行派生器保持独立编译 | SQL 参数、连接池、事务、chrono 编解码、FromRow、原生 SQLite FFI 边界 |
| 加密基础 | 哈希接口、块缓冲及算法共同类型合入 `crypto/digest-traits` | SHA-256 标准向量、HMAC、密码验证与状态类型一致性 |
| 同步与并发 | 锁 trait、停车机制及具体锁收拢；并发工具、epoch、队列及工作窃取收拢 | 锁竞争、原子操作、内存回收及队列语义 |
| 正则与 URL | 正则语法、自动机、字面量和匹配器收拢；URL、域名处理、转义及表单编码收拢 | Unicode 匹配、域名规范化、查询参数及编码边界 |
| 配置与压缩 | TOML 的编辑/日期/输出配套实现收拢；DEFLATE、gzip/zlib 与 Adler 校验收拢 | 原有配置类型、流格式、解压与校验 |
| 浏览器绑定 | WASM 属性宏及实现合并；绑定生成直接进入资源工具进程 | 宏与生成器共享项目内部协议，真实 WASM 导入和启动 |
| 浏览器界面 | 组件属性解析与构建器按 CSR 用途定制，响应式 DOM 配套实现收拢 | 属性、泛型、children、context、Portal、生命周期和失败诊断 |
| 资产编译器 | JS/CSS 编译阶段及仅供它们使用的辅助代码归入 `assets/compiler` 的真实模块 | AST 解析、语义校验、模块边、压缩、字符串/正则字面量和 CSS 含义 |

ZXS 已合并实现是参考来源。仅在原始包版本及归档 SHA 相符时沿用其源码，再适配博客实际接口。SQLite 的 chrono 与 FromRow、序列化属性协议、博客现有 Tokio 版本等按博客需要保留。ZXS 的精确 Git revision、输入档案和逐文件摘要另外登记，避免依赖一个会变化的相邻工作目录。

## 保留的边界

过程宏和普通运行库分别编译，不能为了减少包数把不同 crate 类型硬塞到一起。不同 Rust 语法树代际、不同 PHF 表类型和项目现有 Tokio 接口也按真实类型/协议保持边界；继续减少这些包需要实际迁移消费者，而不是修改名字。

公有组件接口和组件编译器保留禁止 unsafe 的约束。DOM 内核、资产编译器底层和 SQLite FFI 的内部实现按各自安全约束维护。类型身份在同一产品内必须一致，尤其是序列化、Future、HTTP Body、哈希与锁接口。

删除未使用的 RSX、服务端界面、水合、岛屿、拆分加载、编译期数据库访问等能力后，维护范围明确为博客的 Linux 原生服务、宿主资源编译和浏览器 CSR。未来新增用途需要实现相应能力并补实际消费者验证。

## 已测量结果与待证明事项

上一轮构建的 WASM 从 3,306,671 字节变为 3,282,076 字节，gzip 从 1,011,720 字节变为 1,006,449 字节；原生程序从 32,868,720 字节变为 32,894,504 字节。原始与当前制品的摘要、构建身份和浏览器报告保存在本地 `.local-run/customized-source/validation-final.json`。这些是制品大小记录，不能解释为每项合并的独立效果。

当前功能测试、完整离线源码核验和真实浏览器验收已经执行。尚无同环境的冷构建、开发修改后的重编译、峰值内存或请求延迟对比，不能据此称为最优实现。35 个 JS/CSS 阶段的合并尤其需要比较编译粒度：一个 crate 内的真实模块整合可以简化所有者和依赖声明，但修改任一阶段会使整个 crate 失效，且可能减少 Cargo 在这些阶段之间的并行机会。根开发配置目前禁用增量编译，必须把这一条件纳入实验；不能只凭图变小就保留这个边界，也不能未经测量立即重新拆包。

SQLite 的合并保留了查询引擎、驱动、过程宏及原生 FFI 的实际分工，但内部算法大部分沿用已有实现。当前验证主要覆盖博客真实 SQL 消费者，保留的上游测试文件并非全部已注册执行；查询性能未经前后测量。未使用的 `tokio-stream` 声明和实现已在后续审查中移除；公开根接口的通配导出及配置、网络辅助模块仍需逐项验证后再精简。

250 的硬门禁已经移除。来源验证仍统计超过该数的真实源码与完整图；管理器回归用 251 个实际包验证 refresh 和 verify 正常运行。后续工作按已确认的问题和净收益推进，不要求维持当前 240 包或继续缩小数量。

## 按行为修正实现

后续跨层审查、去重和新增回归见[内建依赖实现审查](dependency-review.md)，包括 SQLite、HTTP、Base64、DOM 生命周期及 JS/CSS 链接修复。

本轮复核发现并修正了与包数无关的具体问题：

| 问题 | 修正与验证范围 |
| --- | --- |
| 常量模板拼接遗漏分隔符或覆盖已写入内容 | 保留写入位置，在非空 class/style 片段之间插入分隔符；覆盖 const 求值、Unicode、空片段、4095 字节上限和真实 tuple 模板消费者 |
| 非法组件属性名触发过程宏 panic | 解析并完整校验单一 Rust 标识符，返回绑定原属性位置的 `syn::Error`；拒绝空白、关键字及注释伪名称，保留合法 Unicode 和 raw identifier |
| 原生 local custom executor 安装后影响其他线程 | 本线程安装一次的 TLS 覆盖，其余线程继续使用自己的覆盖或全局执行器；验证线程隔离、回退和重入。该未被博客使用的自定义入口不在 WASM 提供，浏览器保持原有直接函数表调度 |

这些修复不改变包数。它们按错误行为、明确契约与实际消费者验收，不能扩大解释为所有包已经逐一达到最优。

## 验证与维护

核心验证包含认证与存储测试、HTTP 和资产响应测试、真实组件消费者、Unicode 命名语料、标准哈希向量、压缩与配置消费者、JS/CSS 语义回归，以及实际 WASM 编译。候选程序还需要从当前源码生成前端与原生程序，核验构建收据，再进行浏览器登录和业务交互。

包数量下降、删除的独立构建环节及资产查找比较次数可以直接核对。构建时间、内存、WASM/原生文件体积和请求延迟应分别测量，不能由包数推算。

来源维护采用追加迁移：输入身份、输出身份、合并保留的来源和明确退役的来源都要登记；原始归档、许可证和历史记录保留。维护步骤见[源码维护规则](RUST_SOURCE_MAINTENANCE.md)。
